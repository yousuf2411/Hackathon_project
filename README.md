# Who Stays On? — Shapla Shopping Complex

An offline-first hackathon prototype for planning which shops receive generator power during load shedding. It includes a browser dashboard, a local JSON API, input validation, fuel/capacity/dark-run constraints, per-hour explanations, JSON downloads, and a print-friendly A4 roster.

## Requirements
- Python 3.10 or newer (no third-party packages required)
- Any modern browser
- No internet connection required at runtime

## Start
**Windows:** double-click `run.bat`, or open PowerShell in this folder and run:

```powershell
python app.py
```

Then open **http://127.0.0.1:8000**. Stop the server with `Ctrl+C`.

## API
`POST /api/roster`

- Request body: the input JSON object (`sample.json` is a working example).
- `200 OK`: a valid input, with `status: "ok"` and a roster, or `status: "infeasible"` if the hard constraints cannot be satisfied.
- `400 Bad Request`: malformed JSON or invalid input, with `status: "invalid_input"` and a field-specific message.
- `GET /api/health`: simple local health check.

The web screen calls this same endpoint. The app binds to `127.0.0.1` and makes no external requests.

## Where the logic lives
- `app.py` — validation, fuel lookup, roster planner, and HTTP API.
- `index.html` — dashboard, JSON editor/upload, roster board, hourly fuel/load, explanations, downloads, print view.
- `sample.json` — the five-shop worked example from the brief.
- `minute150.json` — a recomputed input where the previously grid-on 16:00 slot becomes an outage.
- `evidence/` — example API outputs and boundary-check evidence.

## Planning method and important limitation
The planner uses a bounded beam search across outage hours. It checks mandatory shops, generator capacity, the combined-load fuel lookup, the total fuel budget, and consecutive-dark limits before accepting a plan. It favors higher total slot value and then lower fuel use. This is a practical dependency-free approach for the 12-shop input size, but beam search is heuristic: for some large inputs it may not prove the mathematical global optimum. Equal-value feasible plans are acceptable under the brief.

## Input format
- `grid_available`: exactly 10 booleans for 10:00 through 19:00; `true` means grid power is available.
- `generator_capacity_kw`: positive whole number.
- `fuel_budget_litres`: non-negative number with up to two decimal places.
- `fuel_table`: ascending combined-load levels and litres/hour. The last level must cover the generator capacity. A non-zero load uses the first level that is at least the combined powered load; zero load uses zero fuel.
- `max_consecutive_dark`: non-negative whole number.
- `shops`: up to 12 shops, each with unique `id`, positive whole-number `kw`, `type` (`mandatory` or `normal`), and 10 non-negative whole-number `value_per_slot` values.

## Output format
Successful output contains `status`, `roster` (one entry per outage hour with `hour`, `slot`, `powered_ids`, `dark_ids`, `load_kw`, `fuel_litres`, `value`, and `dark_reasons`), `value_total`, `fuel_total_litres`, `dark_hours`, and `message`. Grid-on hours are omitted from the API roster because all shops run on grid power; the dashboard still displays them as neutral GRID cells.

## Evidence
- `evidence/sample_output.json` and `evidence/minute150_output.json` are generated by running the actual local API solver on the two included public inputs.
- `evidence/boundary_check.json` tests a mandatory shop whose load exceeds generator capacity and records the expected infeasible result.
- `evidence/combined_load_trap.json` documents a classic incorrect approach (charging fuel separately per shop rather than once for combined load) and the corrected rule.

## Print
Use **Print A4 view** in the dashboard and choose A4 paper in the browser print dialog. The print stylesheet hides the input controls.
